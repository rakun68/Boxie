# A harness for Gemini, and what a software factory needs

Researched and built 2026-11-07, after research/implement-2026-11-07.md. Question: Gemini 3.8 Flash
is the default implementer. What does it need from the harness, and what is Boxie missing as a
software factory?

Tags follow research/workflow.md: **[S]** sourced, **[M]** measured here, **[I]** inference.

## 1. Where Gemini's time goes [M]

All Gemini runs under `runs/` that are not benchmarks: 493 runs with a step stream, 2026-10-12..11-06.

**Model steps, not tools, take the time.**
- Model time across all steps is about 112 h. Bash took 22 h, 16 h of it narrow test runs. Read, grep and edit
  took under 1 h together.
- A step's median time grows with the context:

| context | steps | median step | p90 | hours |
| --- | --- | --- | --- | --- |
| 0-40k | 5269 | 3.8 s | 15.5 s | 10.9 |
| 40-80k | 10022 | 4.4 s | 21.8 s | 28.9 |
| 80-120k | 9040 | 5.6 s | 28.6 s | 35.0 |
| 120-160k | 5783 | 6.5 s | 34.3 s | 25.0 |
| 160-200k | 727 | 7.9 s | 26.1 s | 2.7 |
| over 200k | 2511 | 9.4 s | 25.0 s | 9.5 |

**Gemini pages through files.**
- 10880 of its 12584 reads asked for 100 lines or fewer. The commonest limits were 40, 30, 50, 60 and 25.
- `read` then `read` was the commonest pair of calls (5925 times).
- The median run made 27 tool calls before its first edit, and the p75 run made 58.

**Timeouts are long work, not idle loops.**
- 14 implement runs hit the cut, at 1 to 1.9 h each. None of them wrote a report. Their median was about 260 steps,
  and up to 36M cache-read tokens.
- Identical repeated calls with no edit between them were 4.7 % of calls in timed-out runs and 3.0 % elsewhere.
  So the cut comes in the middle of real work.
- Other verdicts: 7 interrupted, 3 error, 2 setup failed, out of about 200 implement runs.

**Bench**: Gemini passed the last 17 core runs. The core suite cannot tell harness versions apart any more.
Two real-history Lykos tasks (`lykos-peak-wrap`, `lykos-rewind-past-50`) lost their base commits when the
Lykos history was rewritten (the 2026-10-29 backup bundle).

## 2. What the sources say [S]

**Anthropic, effective harnesses for long-running agents**
(https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents):
- An initializer session writes `init.sh`, a progress file, a first commit and a JSON feature list with
  every feature failing. Coding agents may change only the `passes` field.
- Each session does one feature. It starts by reading the progress file and the git log and running a
  basic end-to-end check, and ends committed and "appropriate for merging".
- Failure modes and their fixes:
  - one-shotting the whole app: one feature a session;
  - declaring victory early: the list starts failing;
  - marking done without an end-to-end test: browser automation.

**StrongDM's software factory** (Simon Willison, https://simonwillison.net/2026/Feb/7/software-factory/):
- Specs and scenarios drive agents, with no human writing or reviewing the code.
- Scenarios are end-to-end stories "often stored outside the codebase", a holdout set, because agents
  wrote code that returned true for tests and rewrote tests to match bugs.
- The result is "satisfaction", the share of scenario trajectories that likely satisfy the user. It is
  not a green suite.
- A Digital Twin Universe of the third-party services lets thousands of scenarios run an hour.

**HumanLayer, advanced context engineering** (https://humanlayer.dev/blog/advanced-context-engineering):
- Research, then plan, then implement. Review hardest at research and plan, because "an error in a plan
  can produce hundreds of bad lines".
- Keep context at 40-60 % and compact on purpose into a progress file. Subagents are for context control.

**The Ralph playbook** (https://claytonfarr.github.io/ralph-playbook):
- One task a loop, fresh context each time, and the state on disk.
- Backpressure: tests, builds and lints reject bad work before the commit.
- "Don't assume not implemented": search before building. A short operational AGENTS.md holds the real
  build and test commands.

**The Scaffold Effect in Coding Agents** (ICML 2026, https://icml.cc/virtual/2026/82739):
- On one model, the harness changes tokens per solved task by up to 40x, but pass rate by only 0-8 points.
- OpenCode's own failure fingerprint is "idle loops and TIME failures". Idle turns are "a per-task wait
  tax".

**Harness² (Google Cloud AI Research)**: Gemini 3.5 Flash in OpenCode went from 72.4 to 80.8 on
WorkBuddy-Bench with harness edits written by Claude Opus. The gains were not uniform across harnesses.

**Gemini 3 agent reports** (ADK issue 48, the Google AI forum): it stops after a tool result, loops on
self-correction, and needs explicit stop-and-report instructions and validated tool arguments.

What follows for Gemini [I]: the harness changes cost and time more than pass rate. Gemini's time is
model steps, and each step costs more as context grows. So Boxie should cut steps that carry little and
end a run in a usable state.

## 3. Boxie against a software factory [I]

| factory piece | Boxie |
| --- | --- |
| spec before code | task file, contract plus critic, council (`advise`) |
| acceptance tests before code | sealed tests, which a loop requires |
| isolation | one disposable container a run |
| backpressure | syntax check on every edit, red check, test gate, base suite, neighbour tests |
| fresh, skeptical evaluator | open-code-review, another family for a spec review |
| fix until it passes or stalls | `loop`: stall detection, fresh attempts, selector |
| decomposition | ticket mode, `couple` |
| progress on disk | loop state, parked sessions, ledger |
| measurement | ledger, `stats`, bench with hidden checks |
| **holdout scenarios** | `loop --holdout` (new, §4) and the bench's hidden checks |
| **satisfaction over trajectories** | none: one pass/fail |
| **end-to-end or browser checks** | none built in |
| **digital twins** | none: a project's own fakes only |

## 4. What was built

**Decision** `[4]` **Read widening** (`READ_MIN_LINES=150`, `image/plugin.js`).
- A read asking for fewer lines gets 150, and the offset stays. The OpenCode binary passes the same `args` object
  to `tool.execute.before` and then to the tool (`trigger("tool.execute.before",…,{args:b}); k.execute(b,Q)`),
  so the change applies. A real run's step stream shows the widened `limit`.
- Replayed over the 493 Gemini runs' 12584 reads. A read counts as saved when an earlier widened read of
  the same file, with no edit between, already covered its range. This is an upper bound: it assumes the
  model notices it has the lines.

| minimum | reads saved | steps saved | extra lines a run |
| --- | --- | --- | --- |
| 100 | 23.1 % | 8.7 % | 787 |
| 150 | 29.1 % | 10.9 % | 1486 |
| 250 | 36.4 % | 13.7 % | 2778 |
| 400 | 41.0 % | 15.4 % | 4618 |

- 150 was chosen. Going to 250 nearly doubles the added context for 2.8 more points of steps, and every later
  step costs more with context (§1).

**Decision** `[5]` **Wrap-up note** (`WRAP_MIN=8`).
- `run-task.sh` writes the cut's epoch to `/out/deadline`. Eight minutes before it, one note rides on a tool
  result: stop exploring, get to a state that builds and passes, commit, and report what is done and what is not.
- Why: the 14 timeouts ended mid-work with no report, and Anthropic's harness ends each session clean.
- Unmeasured on the bench, which cuts no run.

**Fixed along the way**: OpenCode runs every function the plugin module exports as a plugin. Exporting
two helpers made every run fail on its first step ("UnknownError"). The module exports `Boxie` alone now,
and a test pins it.

**Decision** `[6]` **Holdout acceptance tests** (`loop --holdout DIR [--holdout-cmd C]`, `LOOP_HOLDOUT_FIXES=2`).
- StrongDM's scenarios as a loop gate. When the loop would approve, a check container copies `DIR` (repo paths,
  like a bench task's `hidden/`) onto the branch and runs them.
- On a failure the fixer gets the last 80 output lines, the test names and messages, and never the source or
  the paths. Then the fix is reviewed and the holdout runs again. After two such rounds the orchestrator decides.
- Why: a sealed test is visible, and a worker can fit the code to it. A holdout measures what the user meant.
  It is the same idea as the bench's hidden checks, used while building.
- The orchestrator writes it. The loop does not check that it fails on the base.
- Ran for real on 2026-11-07 (`hold-loop` on the clikit-sort fixture, the report-sort task's `hidden/` as the holdout):
  Gemini implemented in 394 s, open-code-review found nothing that blocks, the holdout passed in a check
  container (exit 0), and the loop approved. The same holdout on the base exited 1. Its log was mostly
  `node:internal` stack frames and the holdout's paths, so the fixer message now drops frames and assertion
  bookkeeping and writes `<held-back test>` for each path. What is left is the 7 failing test names with expected
  and actual. The fail-then-fix path is tested only against the stand-in harness.
- The critic fallback ran live in the same run: Sol answered HTTP 400, then Luna answered in 12 s with 2 gaps.

**Decision** `[7]` **The critic tries a list of models** (`CONTRACT_MODEL="cx/gpt-6.1-sol-high cx/gpt-6-luna"`).
- On 2026-11-07, after OmniRoute restarted, Sol 6.1 left its live catalog ("not available in the active live
  catalog for provider 'codex'"). Every critique failed with HTTP 400, and the run went on without one.
- Now each model is tried in order, then `CONTRACT_MODEL_ALT`, skipping the implementer's family.
  `contract-critic.json` keeps the failed ones under `failed`.
- Luna 6 answered the report-sort contract in 3 s with two fair gaps (mixed numeric and text columns). Terra
  5.6 high took 93 s.

- **Update, same day**: Codex is not used for advice now. The same report-sort contract, sent to the models left
  (\`max_tokens\` 16000): DeepSeek Flash high and low, and V4 Pro high, spent the cap on reasoning with no answer.
  V4 Pro low (156 s) and Flash none answered "no gaps". V4 Pro none (5 s) listed three gaps the contract already
  covered. Gemini 3.8 Flash high (18 s) and medium (25 s) answered "no gaps". Luna 6 had found two real gaps. So
  \`CONTRACT_MODEL\` and \`CONTRACT_MODEL_ALT\` are empty by default and the critic is off. One contract only.
- \`ROLE_advise\` is DeepSeek V4 Pro high. Through \`ask\` (its own prompt, one retry at low effort with a 32768
  cap) it named short rows and empty cells against \`Number("")\` in 205 s.

**Decision** `[8]` **`doctor` checks the catalog** (`lib/catalog.mjs`). Every model that `boxie.conf` and
`boxie.local.conf` name (`ROLE_*`, `*_MODEL*`) is checked against OmniRoute's `/models`. Run now, it warns:
`cx/gpt-6.1-sol-high (ROLE_advise), cx/gpt-6.1-sol-high (CONTRACT_MODEL)`.

**Fixed**: a bench run that never started showed only "verdict none". The launch error ("no image
boxie-rakunminiitems:latest") was only in a hidden log. `bench` now prints it.

**Not built:**
- A lower `COMPACT_AT` for Gemini. Steps above 80k took 72 h of 112 h, but each compaction made workers
  re-read files (RakunMiniItems #50: 89 re-reads over 5 compactions). It needs its own A/B.
- Satisfaction over many trajectories (StrongDM). One pass/fail per check for now.
- Browser or end-to-end checks, and digital twins. No project here needs them yet.

## 5. Benchmark [M]

`runs/.tmp/ab-harness.sh`. Arm A is `READ_MIN_LINES=0 WRAP_MIN=0`, arm B is `READ_MIN_LINES=250 WRAP_MIN=8`. Both use the same image,
one container at a time.

| task | arm | result | seconds | steps | median step | median context |
| --- | --- | --- | --- | --- | --- | --- |
| real/lykos-t188-prune | A | timeout, hidden check passes | 3685 | 319 | 5.1 s | 108k |
| real/lykos-t188-prune | B | timeout, hidden check fails | 3740 | 101 | 19.0 s | 86k |
| core/feature-report-sort | A | pass | 995 | 36 | 10.1 s | 35k |
| core/feature-report-sort | B | pass | 565 | 36 | 5.2 s | 39k |

- **The t188 pair says nothing about the change.** B's steps were slow from the start: 38 s median in its
  first third, at 49k context. A took 4.0 s at 95k. B ran six hours after A (18:29 against 12:26), because
  the Podman VM stopped mid-bench. The gateway's latency changed, not the harness.
- report-sort: the same 36 steps. Its files are short, so only 6 of 13 reads were widened. The seconds
  follow the gateway's latency that hour. An earlier pass on the same task took 277-571 s.
- B's t188 run got the wrap-up note ("About 8 minute(s) left") and still timed out without a report. The run
  was too slow to finish anything in 8 minutes. **Unmeasured**: whether the note helps a run at normal speed.
- rakun-lifesteal did not start in either arm: the project image was never built under the `boxie-` name.
- The contract critic failed in all of these runs (Sol 6.1 gone, Decision 7).
- **What would measure it**: run the arms interleaved within the same hour, several times, and compare steps
  and reads, not seconds. The replay in Decision 4 is the evidence used here.
- Gemini's step latency changed about 4x across one day. Any time-based harness A/B needs pairs run back to back.
